# 설계 의사결정 기록

실행 방법은 관련 가이드에 두고, 여기에는 요구사항, 선택 이유와 비용을 기록한다. 구현과 검증 완료는 구분한다.

## 2026-11-05 — dbt DQ 저장 단위와 도메인 실행

### 요구사항

기존 Spark는 각 검증 Job에서 공통 `write_event_dq()`를 호출해 모든 오류를 `lakehouse.silver.event_dq` 하나에 MERGE한다. 전체 오류를 한 곳에서 모니터링하기 편한 구조다. dbt 이관에서도 오류 추출 코드를 복제하지 않고, 도메인은 독립적으로 실행하되 도메인 내부의 여러 단계는 명령 하나로 실행하고자 했다.

### 검토한 대안

| 구조 | 이점 | 비용 |
| --- | --- | --- |
| 공통 DQ 모델이 모든 도메인을 UNION ALL | 단일 테이블 모니터링 | 모든 도메인 입력에 의존하며 상위 모델 선택 시 실행 범위 확대 |
| 도메인별 DQ 모델과 향후 통합 조회 | 도메인별 독립 실행 | 물리 테이블 수와 통합 조회 관리 증가 |
| 공통 writer를 post-hook 등으로 호출 | 기존 Spark 방식과 유사 | 모델 저장과 DQ 쓰기의 부분 실패 및 동시 쓰기 처리 필요 |
| 단계별 run → DQ → test 호출 | 각 단계 직후 오류 저장 | 실행 명령과 단계 선택 로직 증가 |

### 현재 선택과 이유

예약 도메인에는 `booking_event_dq` 모델 하나를 둔다. 단계마다 DQ 모델을 추가하는 구조는 아니다. 현재 입력은 예약 이벤트 오류뿐이다. 공통 `event_dq_rows` 매크로로 오류 SELECT와 키·컬럼 구성을 재사용한다. dbt 모델 하나가 하나의 결과 테이블을 관리하는 구조를 유지하면서 도메인 간 실행 의존성을 줄이기 위한 선택이다.

검증 중간 모델은 table로 저장한다. ephemeral은 SQL 코드는 공유하지만 정상·오류 모델에서 입력 읽기와 계산을 반복할 수 있다. table은 파일 쓰기·읽기 비용이 생기는 대신 두 모델이 같은 검증 결과를 읽고 중간 결과를 조회할 수 있다. 같은 파이프라인이 동시에 실행돼 중간 테이블을 교체하지 않도록 해야 한다. 성능 우위는 측정하지 않았다.

실행은 `booking` selector와 `make dbt-booking`으로 묶는다. 중간 모델과 하위 모델을 선택하므로 사용자가 중간 모델 이름을 기억할 필요가 없다. `ref()`로 연결한 current 등은 하위에 포함되지만 각 단계에서 같은 DQ 모델을 반복 실행하는 것은 아니다. 다른 도메인이 하위에 연결되면 selector 범위도 재검토한다.

입력 오류는 격리하고 결과 테스트는 변환 로직의 오류를 탐지한다. 테스트 실패가 이미 저장한 테이블을 롤백하지는 않는다. 독립적인 작업은 계속 실행하고 실패한 테스트에 의존하는 후속 작업을 건너뛰는 기본 정책을 사용한다.

### 남은 결정과 검증

- 모든 도메인의 오류를 함께 보는 통합 조회는 후속 과제이며 Gold 업무 지표와 같은 계층일 필요는 없다. 결제 DQ는 아직 구현하지 않았다.
- current의 JOIN·현재 상태 재구성 오류는 앞단 이벤트 검증만으로 보장되지 않는다. current 테스트와 오류 저장 정책은 해당 모델 이관 시 결정한다.
- 여러 단계의 오류를 예약 DQ에 연결하면 실행 의존성도 늘어난다. 현재 MERGE 키는 Spark와 같은 `dq_key`이며 단계별 오류를 각각 보존하려면 검증 단계를 키에 포함할지 재검토한다.
- 신규 입력 경계, 입력 snapshot ID 보존, 빈 입력 보호와 해결된 오류 표시 정책은 후속 과제다.
- 예약 전용 음수 가격 fixture를 제공한다. 새 DQ의 실제 MERGE, 재실행 시 최초 발견 시각 보존과 selector 전체 실행은 이 기록 작성 시점에 검증 완료로 간주하지 않는다. 기존 clean의 8개 테스트 통과 이력과 구분한다.
